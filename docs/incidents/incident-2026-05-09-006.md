# 削除済商品の復元手段が無く、AI 抽出のトークンを節約しづらい

## 1. 発生日時・症状（ユーザー視点）

- **発生**: 2026-05-09（incident-002 の復元 UI が future-improvements に積まれていた状態）
- **検知**: 佐川「AI 商品作成の節約のために、削除した後この商品を元に戻せる準備して欲しい」
- **症状**:
  - **正しい動作**: 誤削除や撤回に対して「元に戻す」操作で `deleted_at = NULL` に戻せる
  - **実際の動作**: 復元手段が無く、SQL を直接叩くか、AI ラベル抽出から再登録するしか無い → AI トークン消費 + 手間

## 2. 影響範囲

- **対象ロール**: admin
- **対象テナント**: 全テナント
- **影響件数**: 削除した商品数 × 復元したい確率
- **業務影響**:
  - AI ラベル抽出 1 回あたり数〜数十円の API コスト（model: claude-sonnet-4-6, max_tokens: 2000, 画像 1〜3 枚）
  - 撤回判断のフットワークが重くなる

## 3. 原因（技術的根本原因）

- 元々 incident-002 で「ソフト削除」を入れたが、「復元」は future-improvements P2 として後回しにしていた
- 運用シミュレーションを始めると優先度が上がった

## 4. 対応

### 4-A. Server Action

- `app/(admin)/admin/products/actions.ts` に `restoreProduct(id)` を追加
  - `UPDATE products SET deleted_at = NULL WHERE id = ?`
  - `DELETE FROM cart_archive_notifications WHERE product_id = ?`（再削除時に dedup を再起動）
  - `revalidatePath("/admin/products")` + `updateTag("products")`

### 4-B. アーカイブビュー（商品台帳のタブ切替）

- `app/(admin)/admin/products/page.tsx` を全面書き換え:
  - `searchParams.view === "archived"` で表示モードを分岐
  - active: `is("deleted_at", null)`
  - archived: `not("deleted_at", "is", null)`
  - 逆ビューの件数を head + count で取得しタブにバッジ表示
  - アーカイブビューでは「新規登録」ボタンは非表示、復元のヒント文を表示
  - タイトル / 説明文を切替

### 4-C. RestoreProductButton

- `components/admin/RestoreProductButton.tsx` 新規:
  - クリック → `window.confirm` で「復元しますか？」
  - OK → restoreProduct → reload
  - 失敗時はインライン表示
  - スタイル: forest（復元 = 戻す）

### 4-D. AdminProductList

- `mode: "active" | "archived"` prop を追加
- archived 時は edit/delete ではなく **RestoreProductButton** を表示

### 4-E. 検証手順

- `npx tsc --noEmit` ✅
- 商品台帳で削除 → 「アーカイブ」タブにバッジが付く → タブクリックで復元一覧 → 復元ボタン → 通常タブに戻る
- 同じ商品を再度削除 → カート通知 dedup がリセットされ、buyer に再通知される

### 4-F. ロールバックプラン

- 4 ファイルの diff を revert すれば従来挙動に戻る
- DB スキーマ変更なし（`deleted_at` カラムを使い回しているだけ）

## 5. 学び（次回どう動くか）

- **再発防止**:
  - ソフト削除設計を入れる時は「復元」も同時にスコープに入れる
  - dedup テーブルを使う場合は **逆操作（復元）時の clear** を必ず設計する
- **チェックリスト追加（ソフト削除実装時）**:
  - [ ] `<entity>.deleted_at` カラムは追加したか
  - [ ] 一覧クエリに `IS NULL` フィルタは入れたか
  - [ ] 削除前モーダルで影響を可視化したか
  - [ ] race 防止トリガーを書いたか
  - [ ] **復元 UI を作ったか / future-improvements に明記したか**
  - [ ] **dedup を使うなら復元時に clear する設計か**
- **設計上の教訓**:
  - 「復元」は「削除」とセットで設計すべき。後付けにすると UX 設計が浅くなる
  - AI 機能のコスト視点（トークン消費）が運用判断に効く。ボタン 1 つで救えるなら作る価値が高い
