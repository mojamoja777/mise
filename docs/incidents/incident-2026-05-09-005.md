# カート内商品が削除された時、buyer に何の通知も無く静かに消える

## 1. 発生日時・症状（ユーザー視点）

- **発生**: 2026-05-09（incident-004 の削除前モーダル実装直後の運用フィードバック）
- **検知**: 佐川による運用シミュレーション
- **症状**:
  - **正しい動作**: 削除された商品を持っていた buyer が、カート画面を開いた時に「○○ は商品登録が削除されたためカートから削除されました」と気づける（バナー + チャット通知）
  - **実際の動作**: カートから商品が黙って消える（既存の `syncCartAction` は「受付終了」と表示するが、削除と区別できず、チャット通知も無し）

## 2. 影響範囲

- **対象ロール**: buyer（カートに商品を入れていた飲食店）
- **対象テナント**: 全テナント
- **影響件数**: admin が商品を削除するたびに、その時点でカートに入れていた buyer 全員
- **業務影響**:
  - buyer の信頼を損なう（買おうとしていた商品が無断で消える）
  - 後日「あの商品どこ行った？」という問い合わせが発生する

## 3. 原因（技術的根本原因）

- **設計欠如**: 商品ソフトデリート（incident-002）実装時、buyer 側のカート整合性は `syncCartAction` の `is("deleted_at", null)` フィルタで対応していたが、「削除である」ことを buyer に伝える経路が無かった
- **カートはクライアント state**: `lib/cart-context.tsx` で localStorage 管理されているため、admin の削除をリアルタイムに push できない
- **チャット通知に dedup が必要**: カート画面は buyer が複数回開く可能性があるため、同じ削除に対して何度もチャットを送る訳にはいかない

## 4. 対応

### 4-A. dedup テーブル

- **新マイグレーション**: `outputs/db/migration_cart_archive_notifications.sql` 追加
  ```sql
  CREATE TABLE public.cart_archive_notifications (
    buyer_id    uuid NOT NULL REFERENCES public.users(id)    ON DELETE CASCADE,
    product_id  uuid NOT NULL REFERENCES public.products(id) ON DELETE CASCADE,
    notified_at timestamptz NOT NULL DEFAULT NOW(),
    PRIMARY KEY (buyer_id, product_id)
  );
  ALTER TABLE public.cart_archive_notifications ENABLE ROW LEVEL SECURITY;
  -- policy 無し → authenticated からのアクセス全閉、service role のみ操作可能
  ```

### 4-B. syncCartAction 拡張

- `app/(buyer)/buyer/actions.ts` の `syncCartAction` を変更:
  - active products と archived products を別クエリで取得
  - archived があれば内部関数 `notifyCartArchived` を呼ぶ
  - 戻り値に `archived: Array<{ id; name }>` を追加
- `notifyCartArchived` の動作:
  1. service role client で buyer の tenant_id を取得
  2. 同テナントの admin を 1 名取得（chat_messages の sender_id 用）
  3. 各 archived 商品について `cart_archive_notifications` に INSERT 試行
  4. PK 競合（既送）なら skip。新規挿入成功時のみ chat_messages を INSERT
  5. メッセージ本文: `「<商品名>」は商品登録が削除されたため、カートから自動的に削除されました。`

### 4-C. cart 画面 UI

- `app/(buyer)/buyer/cart/page.tsx` で archived 専用バナー文言:
  - 通常削除: 「○○ は受付終了のためカートから削除しました」
  - 商品削除: 「○○ は商品登録が削除されたためカートから削除しました（チャットでもお知らせしました）」

### 4-D. 型

- `types/database.ts` に `cart_archive_notifications` テーブルを追加（service client が typed access するため）

### 4-E. 検証手順

- `npx tsc --noEmit` ✅
- buyer でログイン → 任意の商品をカートに入れる
- 別ブラウザで admin 削除（モーダルで確認 → 削除）
- buyer で /buyer/cart を開く → 黄色バナーに「○○ は商品登録が削除されたため…」表示 → /buyer/chat に「「○○」は商品登録が削除されたため、カートから自動的に削除されました。」が admin から届く
- もう一度 /buyer/cart を開く → バナーは出ない（カートから既に消えてる）／チャットも重複して届かない（dedup）

### 4-F. ロールバックプラン

- アプリ: 3 ファイルの diff を revert
- DB: `DROP TABLE public.cart_archive_notifications;`

## 5. 学び（次回どう動くか）

### dedup テーブルのテスト時クリーンアップが必須

実装後の運用テストで「通知が届かない」と再現した時、原因の半分は **過去のテストで dedup レコードが既に挿入されていた**ことだった。本テーブルは「同じ buyer × product への通知は 1 度だけ」が仕様なので、過去テストの記録が新規通知をブロックする。

- **次回検証時のテンプレ**: シナリオ実行前に必ず `DELETE FROM public.cart_archive_notifications;` で全クリア
- **同様の dedup テーブルを使う将来機能でも**: テスト前 cleanup を README やテスト手順に明記する

### dedup と「テスト時のリセット」は表裏一体

「同じ事象を二度通知しない」設計と「テスト時に何度も発火させたい」要件が衝突する。dev 環境では SQL でリセット可能にしておけば運用と検証の両立ができる。

### 一般原則

- **再発防止**:
  - 「ソフト削除」設計を入れる時は、関連する **クライアント state（カート / フィルタ / お気に入り）** への波及をセットで考える
  - サーバ側の状態変化を「気付かれず消える」のは B2B SaaS で致命傷。常に通知経路を設計する
- **チェックリスト追加（破壊的アクション全般）**:
  - [ ] 影響を受ける buyer に「何が」「いつ」「なぜ」消えたか伝える経路があるか
  - [ ] 通知の dedup（同じ事象を複数回通知しないこと）は設計されているか
  - [ ] クライアント state（cart / filter / 設定）も同期して整合させているか
- **設計上の教訓**:
  - **dedup は PK 競合 + INSERT 成功判定で実装が最短**。複雑なテーブル設計は不要
  - **service role client + RLS 全閉の dedup テーブル** はサーバ間通知の汎用パターン。今後も使う
  - クライアント state（localStorage カート）はサーバ真理と必ずズレる。カート画面 open のたびに sync するのが現代的
