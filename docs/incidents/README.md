# Mise Incident Knowledge Base

Mise（B2B ワイン発注 SaaS）の運用ナレッジベース。本番反映した変更・本番で観測した問題・「直さない」判断を一次資料として残し、未来の自分（と AI）が瞬時にコンテキストを取り戻せるようにする。

cadre プロジェクトで実証済みの運用方針を踏襲する（cadre `docs/incidents/README.md` 参照）。

---

## 1. 目的

- **再発防止**: 同種の問題が起きた時に過去の判断・修正経緯を即座に参照
- **引き継ぎ**: 次セッションの Claude / 別開発者がコンテキストゼロから入れる
- **判断の足跡**: 「なぜこう直したか」「なぜ恒久対応を見送ったか」を残す
- **設計改善**: 同じ系統のバグが繰り返されている場合の可視化

## 2. 運用ルール

### 何を記録するか

- 本番反映したクリティカル〜中重大度の修正
- ユーザー報告 → 修正の流れがあった変更
- 内部レビュー / AI レビューで発見したバグの修正
- 「直さない」判断（理由を残す）
- 仕様変更 / 運用ポリシー変更（例: AI Gateway 移行は保留 → 直叩き継続）

### いつ書くか

- 修正コミット直後 〜 push 後 24 時間以内
- 軽微な UI 修正でも、ユーザーから報告があったケースは原則記録
- まとめて 3 件以上溜まると粒度が粗くなるので、こまめに

### ファイル命名

```
incident-YYYY-MM-DD-NNN.md
```

- `YYYY-MM-DD`: 発生日（または検知日）
- `NNN`: 同日内通し番号（001 始まり）

例: `incident-2026-05-09-001.md`

### テンプレート

`incident-template.md` をコピーして起票。

## 3. 重大度ラベル

| ラベル | 定義 | mise での例 |
|---|---|---|
| **Critical** | データ破壊・誤集計・全テナント影響 / 業務停止級 | RLS 抜けで他テナントの注文が見える、請求金額が壊れる |
| **High** | 一部ユーザーの業務ブロック / 重要機能の不具合 | 注文が確定できない、AI 機能が常時 500 |
| **Medium** | 表示・体験の不整合 / 回避策あり | 地域ドロップダウンに該当が無い、タグ入力 split が惜しい |
| **Low** | 軽微な体験問題 / コスメ | 文言の揺れ、アイコン余白 |

## 4. ステータス

- **resolved**: 根本原因まで対応済み
- **mitigated**: 表示修正など暫定対応のみ。根本対応は `future-improvements.md` へ
- **open**: 未対応
- **wont-fix**: 対応しない判断（理由を本文に記録）
