# 商品削除時に確定前注文の店舗が見えない / 削除と注文の race condition で架空注文が成立しうる

## 1. 発生日時・症状（ユーザー視点）

- **発生**: 2026-05-09（incident-002 のソフト削除実装直後の運用フィードバック）
- **検知**: 佐川による運用シミュレーション
- **症状**:
  - **正しい動作**:
    1. 削除前に「どの店舗から確定前注文 / リクエストが来ているか」を admin が確認できる（直接連絡したい店舗があるかも知れない）
    2. 削除と注文確定が同時刻に発生しても、削除済商品への架空注文は絶対に成立しない
  - **実際の動作**:
    1. 簡素な確認ダイアログのみで、店舗情報が見えない → 削除を実行すると、知らないうちに店舗の「受付中」「割当待ち」が無効化される
    2. createOrder の products 取得時点では deleted_at IS NULL でも、INSERT までの間に admin が削除すれば、架空注文が成立しうる（TOCTOU race）

## 2. 影響範囲

- **対象ロール**: admin（商品管理） / buyer（同時に注文中の店舗）
- **対象テナント**: 全テナント
- **影響件数**:
  - 「店舗連絡が必要だが見えない」: 削除時に確定前注文が 1 件でもあれば全件
  - race condition: 同時刻発生が稀なので運用初期は低確率。だが業務拡大で確実に発生する
- **業務影響**:
  - 連絡漏れ → 店舗との信頼問題、誤った注文処理
  - 架空注文 → 在庫不整合、請求書の不一致

## 3. 原因（技術的根本原因）

### 3-A. 削除前情報の欠如

- `components/admin/DeleteProductButton.tsx` は `window.confirm` のみで、注文情報を取得していなかった
- incident-002 で「ソフト削除する」設計を入れたが、UX 層で「誰の注文を握りつぶすか」を可視化していなかった

### 3-B. Race Condition

- `app/(buyer)/buyer/actions.ts` の `createOrder` は以下のフロー:
  1. `SELECT FROM products WHERE id IN (...) AND deleted_at IS NULL` （L91-95）
  2. INSERT INTO orders（ヘッダ）
  3. INSERT INTO order_items
- 1 と 3 の間で admin が `UPDATE products SET deleted_at = now()` を打てば、TOCTOU で架空注文が成立する
- アプリ層の WHERE フィルタだけでは不可能。DB 層での enforcement が必要

## 4. 対応

### 4-A. 削除前モーダル（クライアント側）

- **新 Server Action**: `app/(admin)/admin/products/actions.ts` `getProductDeleteImpact(productId)` を追加。`order_items` ⨝ `orders` ⨝ `users` を `status IN ('pending', 'allocation_pending')` で絞って取得
- **DeleteProductButton 全面書き換え**:
  - クリック時にまず `getProductDeleteImpact` を呼ぶ
  - 確定前注文が 0 件なら従来の `window.confirm` で削除
  - 1 件以上なら **モーダル表示**: 店舗名 / 状態 / 本数 / 注文日 / チャット導線（`/admin/chat/{buyerId}`）
  - モーダル下部に「キャンセル」「それでも削除する」ボタン
- **AdminProductList**: `<DeleteProductButton id productName />` のように product.name を渡す（モーダル見出し用）

### 4-B. DB トリガーで race を完全防止（DB 側）

- **新マイグレーション**: `outputs/db/migration_product_delete_safety.sql` 追加。BEFORE INSERT トリガーで `products.deleted_at IS NOT NULL` を毎回チェックし、削除済なら `RAISE EXCEPTION 'product is archived: %' USING ERRCODE = 'check_violation'`
- **`SECURITY DEFINER`**: buyer の RLS コンテキストでも products.deleted_at を確実に読めるように
- **`SET search_path = public, pg_temp`**: SECURITY DEFINER 関数のセキュリティベストプラクティス
- **末尾に `NOTIFY pgrst, 'reload schema'`**: 前回の incident-002 の学びを適用済

### 4-C. Buyer 側のエラーハンドリング改善

- `app/(buyer)/buyer/actions.ts` の `createOrder` で `itemsError.message?.includes("product is archived")` を判定し、「注文の途中で取り扱いを終了した商品が含まれていたため、注文できませんでした。カートを更新して再度お試しください。」のようにユーザフレンドリーなメッセージを返す（通常注文 / 割当注文の両方）

### 4-D. 検証手順

- `npx tsc --noEmit` ✅
- 確定前注文がある商品で削除ボタン → モーダルに店舗が出る、チャット導線が機能
- 削除確定後、即時にその商品を別ブラウザの buyer 側で注文してみる → 「取り扱いを終了した商品...」エラー（trigger 発火確認）
- 注文履歴の無い商品で削除 → 即時 `window.confirm` のみ表示

### 4-E. ロールバックプラン

- アプリ: 4 ファイルの diff を revert
- DB: `DROP TRIGGER tr_prevent_order_items_for_deleted_product ON public.order_items; DROP FUNCTION public.prevent_order_items_for_deleted_product();`

## 5. 学び（次回どう動くか）

- **再発防止**:
  - 「削除/アーカイブ系」の機能は **アプリ層フィルタだけでなく DB 層 enforcement** を必ずセットで考える
  - admin の破壊的アクションは「影響を受ける関係者が誰か」を可視化してから実行させる UX を標準にする
- **チェックリスト追加（破壊的アクション全般）**:
  - [ ] 影響を受ける他テーブル / 他ユーザを抽出する Server Action はあるか
  - [ ] その情報を UI に出す確認モーダルはあるか
  - [ ] race condition のシナリオ（同時発生）を 2 〜 3 個書き出して、DB 層で塞げているか確認
- **設計上の教訓**:
  - **アプリ層 WHERE フィルタは TOCTOU を防げない**。並行性が絡む不変条件は DB 制約 / トリガーで守る
  - **SECURITY DEFINER + search_path 固定** は SECURITY DEFINER 関数のテンプレート（PostgreSQL 公式推奨）
  - 確認 UI の判断材料は「件数だけ」ではなく「誰に・何を・いつ」まで具体化する
