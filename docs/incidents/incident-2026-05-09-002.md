# 商品削除がサイレントに失敗（FK RESTRICT）+ 注文履歴がある商品の削除挙動が未定義

## 1. 発生日時・症状（ユーザー視点）

- **発生**: 2026-05-09（P0 ランタイム動作確認の途中）
- **検知**: 佐川が商品台帳でゴミ箱アイコン → 確認ダイアログ → OK 押下 → 何も起きないことを発見
- **症状**:
  - **正しい動作**: 削除できる、または「注文履歴があるためアーカイブしました」と通知される
  - **実際の動作**: 確認ダイアログ後にページ reload は走るが、商品が消えない。エラーメッセージも出ない（サイレント失敗）

## 2. 影響範囲

- **対象ロール**: admin（商品管理）
- **対象テナント**: 全テナント
- **影響件数**: 注文履歴がある商品全件（運用開始後ほぼ全商品）
- **業務影響**:
  - 商品の論理削除ができない → 売り切り終了商品が台帳に残り続ける → 買い手カタログにも残り続ける
  - 「削除できないこと」自体は注文履歴保護として正しいが、ユーザに何も伝えていない / 別経路が無いのが致命

## 3. 原因（技術的根本原因）

- **直接原因 ①（DB）**: `outputs/db/migration.sql:137` で `order_items.product_id REFERENCES products(id) ON DELETE RESTRICT`。注文履歴が 1 件でもあると DELETE は FK violation で失敗
- **直接原因 ②（Server Action）**: `app/(admin)/admin/products/actions.ts:156-171` の `deleteProduct` は失敗時に `{ error: "..." }` を返すだけで例外送出しない
- **直接原因 ③（UI）**: `components/admin/DeleteProductButton.tsx:6-10` が戻り値を完全無視し、即 `window.location.reload()`。エラー表示パスが存在しない
- **見落とし**:
  - 削除パスのエラーハンドリングが「成功時しかテストされていない」状態だった
  - 注文履歴のある商品の削除挙動が要件として定義されていなかった

## 4. 対応

- **コミット**: 未（本セッションでまとめてコミット予定）
- **変更内容**:
  - **DB スキーマ**: `outputs/db/migration_product_soft_delete.sql` 新規追加（`products.deleted_at TIMESTAMPTZ NULL` + 部分インデックス）→ Supabase Dashboard で user 実行
  - **型**: `types/database.ts` 128-193 — `products` の Row/Insert/Update に `deleted_at` 追加
  - **Server Action**: `app/(admin)/admin/products/actions.ts` の `deleteProduct` を全面書き換え — `order_items` への参照を `count: "exact"` でチェックし、参照あり → `UPDATE deleted_at = now()`、なし → 従来通り DELETE。戻り値は `{ ok: true, mode: "hard" \| "soft" } \| { ok: false, error }`
  - **UI**: `components/admin/DeleteProductButton.tsx` を全面書き換え — `useTransition` で disabled 制御、ソフト削除時は `window.alert` で「注文履歴があるため非表示にしました」を通知、エラー時は `<span>` で表示
  - **クエリのフィルタ**: 以下に `.is("deleted_at", null)` を追加
    - `app/(admin)/admin/products/page.tsx` — 商品台帳一覧
    - `lib/products.ts` — buyer カタログ（`getActiveProducts`）
    - `app/(buyer)/buyer/actions.ts` — カート検証 / 注文作成
    - `app/api/ai/suggest-allocation/route.ts` — AI 割当提案
    - `app/(admin)/admin/allocations/[productId]/page.tsx` — 割当詳細
    - `app/(admin)/admin/allocations/page.tsx` — 割当一覧（embedded `products.deleted_at` フィルタ）
- **検証手順**:
  - `npx tsc --noEmit` ✅
  - 注文ありの商品で削除 → ソフト削除メッセージが出る、台帳から消える、注文詳細では引き続き表示される
  - 注文なしの商品で削除 → 即消える、Storage の画像も消える
- **ロールバックプラン**:
  - コード: 7 ファイルの diff を revert
  - DB: 即時ロールバックは不要（`deleted_at` カラムが NULL なら従来挙動と同じ）。完全に戻すなら `ALTER TABLE products DROP COLUMN deleted_at;`

## 5. 学び（次回どう動くか）

### Supabase の DDL では NOTIFY pgrst を必須にする

本 incident の対応中、最初のマイグレーション SQL（`ALTER TABLE products ADD COLUMN deleted_at`）が「Success. No rows returned」と表示されたにも関わらず、アプリから `column products.deleted_at does not exist` エラーが返り続けた。原因は PostgREST のスキーマキャッシュが古いまま。`NOTIFY pgrst, 'reload schema';` を末尾に追加して解決。

→ 教訓: **`outputs/db/migration_*.sql` の末尾には必ず `NOTIFY pgrst, 'reload schema';` を入れる**。memory `feedback_supabase_pgrst_notify.md` にも記録。

### 削除フロー一般

- **再発防止**:
  - 削除パスは「成功時」「業務エラー時」「DB 制約エラー時」の 3 パターンを必ず UI で表現する
  - 削除フローのある全テーブルで FK の `ON DELETE` 設定を事前確認し、ハード/ソフトの方針を要件定義に明記する
- **チェックリスト追加（削除機能を実装する時）**:
  - [ ] 対象テーブルへ FK している他テーブルを `\d <table>` で全列挙
  - [ ] FK のうち `ON DELETE RESTRICT/NO ACTION` があるか確認
  - [ ] あればソフト削除 / 履歴保持の方針を決める（DB に `deleted_at` カラム）
  - [ ] 一覧系の SELECT に `WHERE deleted_at IS NULL` を必ず追加
  - [ ] Server Action の戻り値を UI が必ず handle する
- **設計上の教訓**:
  - **`window.location.reload()` だけで完結する Server Action 連携は危険**。戻り値を握りつぶすパターンの典型
  - B2B SaaS では「履歴を保つ削除」が標準。ハード削除はテストデータと紐付けの無いマスタのみ
